本周武汉迎来全面降温。我觉得气温会影响我的打字速度，因为气温低时，我的手指灵活度降低，发现打字速度都降低了不少。当然在公司里还稍微暖和一点。

🔧 有趣的发现

Hallmark：前端设计 Skill 工具包

Github: Nutlope / hallmark 是一个专门改善 AI 生成前端 UI 设计质量的 Agent Skill，配有主题、文档、脚本和检查机制。

其设计思路：通过设计规则 + 主题选择 + 自动检测 + AI Review 来约束 agent 的行为。

我还没有实际用过 Hallmark，但觉得这种思路值得借鉴：在设计 UI/UX 时，用设计规则和检查机制约束 Agent，可能比只写许愿式的 prompt 更容易控制产出质量，减少返工。

📖 值得一读

  • 你不知道的客户端开发：AI 时代下的选型、原生与借力 - Tw93：文章介绍了 Mole 如何让 Mac 和 Windows 两端保持一致：用同一份设计 token 和多语言文件生成界面资源，再用 SYNC.md 对照两端的功能实现与差异。做跨端客户端时，这套做法值得参考。
  • 播客 Rust Talk（小宇宙）：我最近在听的一档 Rust 播客，嘉宾会聊各自的开发经验，以及对 Rust 和行业的看法。想持续关注 Rust 的话，可以听听。

💡 一点思考

编程类 Skill 是否还有必要？

最近读到我的 AI 原生开发流程：一个真实案例的完整复盘 | 宝玉的分享。作者认为，大部分开发类 Skill 已经没必要了，因为现在的大模型在编码方面足够强，简单的自然语言指令就能完成不少任务。我自己的延伸想法是：如果 Skill 对开发过程规定得太细，也可能限制模型根据具体任务作判断。

这个观点让我想到论坛上关于 Superpower 的讨论：有人喜欢它覆盖开发各阶段，也有人觉得它太重，过多约束反而会妨碍模型处理具体任务。我看到的讨论更多集中在它的缺点上，因此猜想有些人可能会转向 OpenSpec 或更轻量的 Skill；这只是我的观察和推测，不代表整体使用趋势。项目规模不同，对这类流程约束的需求可能也不同。

对于我自己，前两个月还在不断优化 SDD 工作流 Skill 集合。现在我想暂时少花些时间追着模型调整开发类 Skill：模型能力变化很快，刚改好的规则可能过不了多久就需要重新评估。先用现有流程做事，遇到明确的问题再改，可能更适合我目前的节奏。

但是文章中作者还提到：对于辅助设计类和自动化类的 Skill 还是很有必要的，比如原型/UI 设计类 Skill，或是一些标准化的、不需要判断但耗时的流程，还是可以沉淀为 Skill 的。

🌱 最近在学

手写编程语言

上周在小宇宙听 Rust Talk 第十六期时，嘉宾在末尾推荐了两本书：《Crafting Interpreters》和《SICP》。《Crafting Interpreters》带着读者动手实现解释器和虚拟机；《SICP》讨论程序设计中的抽象与计算模型，也涉及解释器和编译器。

我觉得在 AI 时代，编程基本功可能不会让你短期内快速赚到更多的钱，但是对于想长期从事编程类工作的人来说，这是提升基本功的好方式。就像《一拳超人》中的琦玉，每天雷打不动的坚持锻炼，不管是不是成为了第一，好歹你是比昨天进步了，不是吗？

解释器的实现虽然偏底层，但书里“解析输入、理解结构、再执行”的过程，也能帮我理解一些日常开发中会遇到的机制。比如 Spring SpEL 会解析表达式，并在给定上下文中求值。我还没有深入研究 SpEL 的实现，想先通过这本书弄懂这类机制是怎么工作的。

我正在读《Crafting Interpreters》，作者提供了免费的在线版本。书中先用 Java 写解释器，再用 C 写虚拟机；作为 Java 后端开发者，我觉得从这本书开始比较容易上手。《SICP》我还没读，只是听了推荐后很想了解，但目前对它的难度有点望而却步。
