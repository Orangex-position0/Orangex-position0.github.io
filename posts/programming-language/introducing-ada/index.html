认识 Ada：关键系统里的编程语言

从温度与压力的例子认识 Ada 的强类型、范围约束和契约，看看它在关键系统中的应用，以及 GitHub 上的生态。

最近在网上闲逛时，我无意间发现了一门以安全性闻名的语言：Ada。作为一个 Rust 爱好者，我有点好奇，它通过哪些机制减少程序中的错误？

Ada 在 1983 年首次标准化，比 C 的首次 ANSI 标准化（1989 年）还早。它是一门通用编程语言，在航空航天、铁路和关键控制系统等领域有公开的使用记录。

先用两个温度相关的小例子，看看 Ada 怎么区分数据的类型、限制数值范围，以及约束一次操作。这里讨论的是这些机制如何发现错误，不展开它与 Rust 在内存安全机制上的比较。

Ada 如何表达合法的数据与操作

场景一：温度和压力，不能因为都是数字就混着用

假设我们要接收传感器数据：温度的合法范围是 -40 到 125，压力的合法范围是 0 到 300。这里的范围只是为了演示语言特性，不对应实际设备。

如果把它们都存成普通整数，就需要额外检查两件事：数值有没有超出范围，以及有没有把压力误当成温度。

Ada 可以直接把这些要求写进类型定义：

type Temperature is range -40 .. 125;
type Pressure is range 0 .. 300;

type 声明类型，range 后面写允许的取值范围，.. 表示包含两端的区间。这里定义的是两个独立的整数类型。

再声明两个变量。Ada 把变量名写在类型前面，用 := 赋值：

Current_Temperature : Temperature := 20;
Current_Pressure    : Pressure := 100;

即使两个类型的取值范围有重叠，也不能直接混用。下面这行代码会产生编译错误：

Current_Temperature := Current_Pressure;

范围约束检查的是另一件事：值是否超出了类型允许的范围。假设 Read_Sensor 是一个返回 Integer 的传感器读取函数：

Current_Temperature := Temperature (Read_Sensor);

这里的 Temperature (...) 表示显式类型转换。如果传感器返回 200，在启用相应运行时检查的情况下，就会触发 Constraint_Error，而不会把它作为合法温度存进去。

温度与压力混用，可以通过类型检查发现；运行时才读到的数据，则需要运行时检查。检查能发现错误，但如何处理错误、让系统继续安全运行，仍然需要程序员设计。

Java 和 Rust 也能表达这些限制，比如用类或 newtype 区分温度与压力，在构造时校验范围。Ada 提供了直接声明整数类型及其范围的语法，不需要先写一套包装和校验代码。

场景二：温度合法，也不代表这次调整就合法

继续用温度举例。假设有一个温控程序，目标温度必须在 -40 到 125 之间，而且每次调整不能超过 5 度。这里限制的是程序中的目标设定值，不是实际设备的升温速度。

从 20 度直接改到 100 度，两个值都符合 Temperature 的范围，但这次调整不符合要求。这个限制取决于调整前后的值，仅靠类型的固定范围表达不了。

Ada 可以把它写成操作的前置条件，再用后置条件说明正常返回时应该得到什么结果：

procedure Set_Target
  (Target : in out Temperature; Requested : Temperature)
with
   Pre  => abs (Integer (Requested) - Integer (Target)) <= 5,
   Post => Target = Requested
is
begin
   Target := Requested;
end Set_Target;

不熟悉 Ada 语法的话，先看这三处就够了（其实我也不熟悉…）：

  • in out 表示参数既可以读取，也可以修改。
  • Pre 是前置条件：调用时，新旧目标温度的差值不能超过 5。这里先转成 Integer 再相减，避免用温度类型本身承载差值计算。
  • Post 是后置条件：过程正常返回时，目标温度必须等于请求的值。

假设当前目标是 20 度，设成 23 度符合前置条件；直接设成 100 度则不符合。在启用契约检查时，后者会在执行过程体之前触发 Assertion_Error。如果以后修改了实现，导致正常返回时没有把目标设成请求的值，后置条件检查也会发现问题。

这个例子的实现只有一行，契约显得比实现还长。不过，接口允许怎样调用、承诺什么结果，都能直接从声明中读到；实现变复杂后，这些要求仍然可以保留。

契约检查需要显式启用，比如使用 GNAT 的 -gnata 选项，或配置 Assertion_Policy (Check)。不能假定写了 Pre、Post，构建出来的程序就一定会执行检查。

以上代码是讲解用片段，尚未编译验证。范围检查和契约检查的行为均以前述检查已启用为前提。

类型、范围和契约各自检查不同的问题，但都需要程序员先写出要求。如果范围本身定义错了，或者契约漏掉了一项业务限制，这些检查并不会自动知道。

原生并发与 SPARK

除了这两个例子，Ada 还把并发任务和同步机制放进了语言本身。任务（task）可以并发执行，受保护对象（protected object）可以协调对共享数据的访问。对需要同时处理多个传感器、控制回路或通信流程的程序，这些机制可以用来组织并发工作；实时调度还涉及优先级、运行时配置等内容，这里先不展开。

SPARK 则用于进一步验证程序。它基于 Ada，包含便于分析的语言限制、验证标注和相关工具，可以在明确的假设和证明条件下，证明某些运行时错误不会发生，或程序满足指定的契约。本文没有运行证明工具，上面的示例只用于说明检查机制，不声称已经完成形式化验证。

Ada 为什么主要活跃在关键系统领域？

这些设计和 Ada 的来历有关。上世纪 70 年代，美国国防部希望统一软件开发使用的语言。当时不同项目使用不同的语言和工具，增加了人员培训、工具维护和代码复用的难度。

其中一些软件需要控制设备、同时处理多个任务，并在规定时间内作出响应。可靠性、实时处理和长期维护，也是设计时需要考虑的要求。美国国防部通过方案竞争选择设计，最终由 Jean Ichbiah 领导的团队提出的方案胜出。AdaCore 的入门资料介绍了这段背景。

具体到应用，AdaCore 在 2022 年发布的 ENYSE 案例中，ENYSE 选择 Ada 和 GNAT Pro 开发无线闭塞中心（Radio Block Centre，RBC）。它负责生成并向列车发送运行许可，告诉列车可以进入哪些区段。Ada 在这里参与的是铁路信号与行车控制系统的开发。

Ada Resource Association（Ada 资源协会）的公开项目清单还列出了 Airbus、Boeing 的多个机型，以及包括中国在内的多个国家的政府空管机构。

这些材料说明了具体的使用方向，但不等于当前部署清单：ENYSE 公告发布时，项目仍处于概念验证演示系统的开发阶段；ARA 清单则没有交代各条目的具体模块和使用时间。不能据此推断它们目前的使用状态。

为什么 Ada 在 GitHub 上这么冷清？

我在 GitHub 上用 language:Ada 搜索，按 star 数量排序，前 20 个项目中五花八门的类型都有：游戏、编译器、操作系统、通用开发工具，甚至还有 Web 框架，但当时没有一个超过 1k star。

有意思的是，排在前列的还有编程博主 Tsoding 的游戏项目 eepers。前面看到的还是航空航天和铁路系统，到了 GitHub 上，却是一个游戏项目吸引了我的注意。

这次搜索只能说明，当时按这个条件找到的热门仓库 star 数不高，不能代表 Ada 的全部项目或工业使用情况。

为什么会有这种反差？我觉得可能和它的应用场景有关。航空航天、国防和工业控制领域的软件，很多是为特定设备或客户开发的，可能涉及保密要求，也未必有公开维护的动力。这可以解释为什么一部分代码没有出现在公开仓库里，但还不足以解释整个生态的热度。

另一个可能的原因是，普通开发者接触 Ada 的机会较少。如果工作中用不到，业余项目又有更熟悉的语言可选，可能就很少会想到它。这些都只是可能的解释，仅凭这次搜索，还不能确定它们各自有多大影响。
