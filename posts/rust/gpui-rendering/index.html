1. Discord 让 GPUI 小火了一把

因为今年将 IDE 从 vscode 换到 zed 时，发现这个 zed 的基础框架 GPUI 十分的好用，也用它开发了几个小工具，但是苦于没有太多比较火热的项目做支撑，导致其热度其实有点不上不下的。因为 Rust GUI 框架还有更火的 tauri、egui、slint 等。

但是就在 2026 年 11 月 8 日，Discord 在 Youtube 官方频道发布了一个视频：宣布其开发团队将开启 Phoenix 计划，也就是将 Discord 的桌面端用 Rust + GPUI 重写。

这属实是让 GPUI 小火了一把。那作为一个 GPUI 框架的爱好者，我希望向你介绍一下 GPUI 框架是什么，以及其独特的渲染机制。

这篇文章会从“像游戏引擎一样渲染”这个说法出发，用一个简化的聊天界面，讲清 GPUI 如何把 UI 元素一步步变成屏幕上的像素，以及 shader、实例化绘制和字形图集在其中起什么作用。即使没有图形学基础，也可以顺着例子理解这套流程。

2. GPUI 是什么？

GPUI 是 Zed 团队开发的 Rust GUI 框架，Zed 编辑器的界面就是用它构建和绘制的。除了绘制界面，它还提供状态管理、事件处理和布局等能力，让开发者能把应用数据、用户操作和界面展示连接起来。

使用 GPUI 时，开发者用 Rust 组合界面元素，设置尺寸、颜色和布局方式，再注册点击、键盘等事件的处理逻辑。比如一个聊天窗口，可以由消息列表、输入框和发送按钮组成，GPUI 负责把这些描述转换成可以交互的界面。它的样式 API 借鉴了 CSS 的一些概念，熟悉 Web 开发的读者会看到 Flex 布局等熟悉的写法。

从名字可以联想到 GPU 与 UI，但“使用 GPU”还不足以说明它与其他桌面框架的区别。先对比几种常见方案的 UI 渲染路线：

方案常见 UI 描述方式谁负责 UI 布局与绘制
ElectronHTML、CSS、JavaScript随应用分发的 Chromium
TauriWeb 前端系统 WebView
GPUIRust 元素与样式 APIGPUI 自己的布局与渲染实现

Electron 和 Tauri 都可以利用浏览器引擎的 GPU 加速能力。GPUI 则为自己的 UI 元素实现布局和绘制流程，可以围绕界面的需要设计渲染管线。

简单来说，就是 GPUI 自己掌控 UI 的布局和绘制管线。

那么，GPUI 怎样把消息列表、按钮这样的 UI 元素交给 GPU 绘制？这就涉及它与游戏引擎相似的渲染思路了。

3. 为什么说 GPUI 像游戏引擎一样渲染？

3.1 游戏引擎的渲染逻辑概述

假设要在一个 2D 游戏中绘制敌人。游戏逻辑关心它有多少血量、是否正在攻击；但渲染阶段需要的是位置、形状、纹理和颜色等底层渲染数据。敌人受伤后变红，游戏逻辑决定何时变红，渲染器根据颜色参数把它画出来。

所以，可简单理解为：游戏引擎是将“游戏场景”转为“结构化的渲染数据”，方便交给 GPU 批量绘制。

比如 Godot 的 2D 渲染机制：

  • Godot 不是直接将整个游戏画面当做一张大图片来处理
  • 而是通过场景树（Scene Tree）先组织游戏对象（比如玩家、敌人、地性等）
  • 然后再将可见对象转为底层渲染数据，比如几何形状、纹理、颜色等
  • 接着通过 RenderingServer 代码管理渲染资源和绘制命令，最终交给 GPU 绘制

再比如 Unity 的 2D 渲染机制：

  • Unity 使用一些组件表示人物、人物位置等可见对象
  • 再根据组件准备底层渲染数据，并通过渲染管线将绘制命令交给 GPU
  • 这样 Unity 的底层渲染器就不必理解“玩家”、“敌人”等业务含义，直接处理几何、材质等底层渲染数据即可

3.2 GPUI 的渲染逻辑概述

GPUI 也采用了类似游戏引擎的渲染逻辑：

  • 应用层声明按钮、消息列表和输入框等 UI 组件
  • 绘制时把它们全部转换成底层图形基元。GPU 不用理解“这是一个 button 组件”，它执行的是针对几何、纹理和像素的计算。

所以，你可以简单理解为：所有上层的 UI 组件都能由底层图形基元组合而成，所以渲染管线直接处理底层图形基元即可。就类似七巧板（待讨论点1：这里可能要换一个更通用的真实案例）

这里用一个简化的聊天界面作例子：

界面内容绘制时可以拆成什么
消息行的背景一个带颜色、尺寸和圆角等参数的矩形
用户头像图像纹理，以及它在界面中的目标区域
用户名和消息正文经过排版的字形及其绘制位置
悬浮提示背景矩形、阴影和文字

一个复杂的界面，可以由有限种类的图形基元组合出来。同一种矩形绘制逻辑既能用于消息背景，也能用于按钮背景，它们的位置、尺寸和颜色可以各不相同。

GPUI 把这些图元组织进 Scene。可以将它理解为当前界面需要绘制的图形数据集合，其中还包含绘制顺序等信息。它与业务层的组件树承担不同职责：组件树描述界面如何组成，Scene 为后续绘制提供结构化的数据。

游戏引擎：游戏对象 → 几何、纹理、变换等渲染数据 → GPU
GPUI：UI 元素  → 矩形、阴影、字形等图形数据 → GPU

“像游戏引擎一样渲染”主要指这里的数据组织和绘制思路。Zed 的官方文章明确谈到了游戏领域带来的启发，以及针对 UI 图元编写专用 shader 的选择。

注意：这不意味着 GPUI 使用了某个现成游戏引擎，也不意味着桌面应用要具备完整的游戏循环。

4. 从 UI 元素到屏幕像素

GPUI 的渲染流程负责把应用状态转换成最终显示的画面。先看其中的主要环节与对象，以及它们各自承担的职责：

环节或对象职责
Render根据应用当前状态，描述界面由哪些元素组成
Layout确定元素的位置和尺寸
Prepaint根据布局结果，准备命中区域等后续需要的状态
Paint将元素的视觉表现转换为绘制用的图元
Scene汇集图元及绘制顺序等信息，供后端使用
图形后端准备绘制资源，将绘制命令提交给 GPU
GPU执行绘制命令，生成渲染结果
Present将渲染结果交给平台显示系统呈现

其中，Scene 是承载绘制数据的对象；Render、Layout、Prepaint 和 Paint 等则描述处理这些数据的不同阶段。表格介绍各自的职责，下面的流程图展示它们如何衔接。

以聊天列表收到一条新消息为例：数据发生变化后，应用请求更新界面。GPUI 需要确定显示什么、每项内容放在哪里，再把图形数据交给后端绘制。

下面是省略缓存和复用细节的概念流程。它不代表每次显示刷新都要重新执行所有步骤。

flowchart TD
    subgraph CPU[CPU 侧]
        A[状态更新并请求渲染] --> B[Render：构建元素树]
        B --> C[Layout：计算布局]
        C --> D[Prepaint：准备命中区域等状态]
        D --> E[Paint：产生图元并组织 Scene]
        E --> F[后端准备资源并编码绘制命令]
    end
    F --> G[GPU 执行绘制]
    G --> H[显示系统呈现结果]

图中画的是数据依赖关系。实际的命令提交、GPU 执行和显示呈现涉及异步调度，CPU 不必逐步等待所有 GPU 工作完成。

4.1 Render：根据状态构建元素树

Render 负责根据应用当前状态构建元素树，描述界面包含哪些元素、这些元素如何组合。在 GPUI 中，应用可以通过实现 Render Trait 来描述这部分界面。

新消息包含作者、正文和头像等信息。应用通过 Render 描述这些内容如何组成界面，比如消息行里放一个头像区域，再放包含用户名和正文的文字区域。

如果你写过 React，可以先用“根据当前状态描述界面”来理解这一步。GPUI 使用 Rust 构建自己的元素树；元素树不会交给浏览器解释，也不会直接成为 GPU 命令。

4.2 Layout：确定位置和尺寸

Layout（布局）负责结合窗口大小、样式和内容测量，确定元素的位置和尺寸。

对于消息行，元素树描述了组成关系，布局则要回答头像应该多大、正文能占多宽、长消息在哪里换行。比如头像占据左侧固定区域，正文使用剩余宽度；正文换行又会影响消息行的高度。

GPUI 的通用元素布局使用 Taffy。自定义元素也可以参与测量，或实现适合自身的布局方式。读源码时会看到 request_layout，它负责申请布局并准备阶段状态，实际布局计算随后确定元素的边界。

4.3 Prepaint：准备依赖布局的状态

Prepaint 是布局完成后、正式绘制前的准备阶段，负责建立依赖元素位置和尺寸的状态，供交互和后续绘制使用。

知道头像的位置后，框架才能准备它的命中测试区域，也就是 hitbox。鼠标移到这个区域时，应用才有依据判断用户正在悬停头像。

4.4 Paint：把元素转换成图元

Paint 负责将元素的视觉表现转换为图元，并组织进 Scene，为后端绘制提供数据。

这时消息背景的位置和大小已经确定，Paint 可以生成对应的矩形数据；头像和正文也会准备各自需要的绘制数据。

4.5 后端与 GPU：执行绘制

图形后端负责把 Scene 中的绘制数据转换为 GPU 可以执行的命令；GPU 负责执行这些命令，生成渲染结果。

Scene 中的图元（Primitive）需要按正确顺序、合适批次提交。Scene 源码中的 finish 和 batches 参与排序与批次组织；平台后端再准备缓冲区、纹理和绘制管线，把命令编码后提交给 GPU。

GPU 随后执行 shader，处理几何位置、纹理采样、像素颜色和混合等工作。前面的 Render 是应用构建界面的入口，这里的 Renderer 则是后端渲染器，二者处在不同层次。

GPUI 自绘与 Electron、Tauri 的区别也体现在这里：

  • 常见的 Electron、Tauri 应用由 Chromium 或系统 WebView 解释 Web UI；
  • GPUI 通过自己的元素、Scene 和图形后端完成 UI 绘制。浏览器同样能利用 GPU，双方采用了不同的 UI 渲染管线。

4.6 Present：提交显示

Present 负责通过平台的呈现机制，将渲染结果交给显示系统。它连接了生成画面与显示画面这两个环节。

Present 与“显示器已经显示这个像素”之间有调度过程，不能直接画等号。

5. GPUI 采用了哪些渲染优化技术？

把界面转换成图元后，GPUI 可以针对这些图元采用专门的绘制和复用方式。下面看三项技术，以及它们分别减少了什么开销。

5.1 专用 shader：根据参数绘制 UI 形状

Shader（着色器）是在 GPU 上执行的程序，参与计算图形的位置和像素颜色等。GPUI 针对 UI 图元使用专用 shader，利用形状的特点完成绘制。

比如绘制一个圆角消息背景，CPU 提供位置、尺寸、颜色和圆角半径等参数，GPU 执行对应 shader 生成形状。调整背景大小或圆角时，改变参数即可，无需为每种外观预先制作和存储一张图片。

5.2 实例化绘制：让多个图元共享绘制逻辑

实例化绘制让多个图元共享绘制逻辑，分别提供各自的数据，通过一次绘制调用处理多个兼容实例，减少逐个组织和提交绘制命令的开销。

比如聊天列表中有许多矩形背景，它们的位置、尺寸和颜色可以不同，但能够共享同一种绘制逻辑。GPU 仍然需要绘制每个背景，减少的是逐个提交它们的开销。

批量提交还要遵守遮挡顺序。例如悬浮提示的背景需要盖住下层消息文字，不能为了把同类图元放在一起绘制而随意改变顺序。

5.3 Glyph Atlas：缓存并复用字形图像

Glyph Atlas（字形图集）是集中存放字形图像的纹理，供绘制时查找和复用。将字形转换为可绘制图像的过程称为栅格化，复用已有图像可以减少重复栅格化的开销。

比如聊天列表中反复出现相同的文字，在字体、字号等条件相容时，可以复用图集中已有的字形图像，再将它们绘制到各条消息对应的位置。

Zed 的官方渲染文章介绍了专用 shader、实例化绘制和字形图集的应用。这些技术为 GPUI 提供了优化空间，实际性能收益仍取决于具体界面、硬件和工作负载。

6. 自建渲染管线意味着什么？

GPUI 让框架开发者能够围绕实际 UI 需要设计图元、shader、缓存和批次组织。消息背景适合哪种绘制方式，文字资源怎样复用，都可以在自己的渲染管线中调整。

与此同时，一个桌面框架还要解决文本输入、焦点、剪贴板、可访问性、窗口系统和图形后端适配等问题。Rust 能跨平台编译，也不代表这些平台差异会自动消失。Zed 的 Linux 移植文章展示了平台窗口与渲染后端之间需要承担的适配工作。

这些成本主要由框架和平台实现承担，应用开发者可以复用 GPUI 提供的能力；如果涉及自定义控件或平台特性，仍可能需要处理更底层的问题。

选择这条路线，意味着用更明确的 UI 问题域换取针对性优化空间。具体能获得多少性能收益，还要结合实际界面、硬件和工作负载测量。对想尝试 GPUI 的开发者，我推荐可以先用 AI 辅助来开发一些需要的小工具，比如日志查看器、番茄钟、todo list 等。
